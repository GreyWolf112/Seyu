## 数据结构

统一记录字段：

| 字段 | 含义 |
| --- | --- |
| id / kind | 唯一标识与 mood/journal/bottle/joy/reflection 类型 |
| date | 用户记录所属日期，迁移保留旧格式 |
| createdAt / updatedAt | 创建和更新时间（毫秒） |
| timePrecision | day 或 millisecond；旧数据只有日期，不能推断精确时间 |
| moods / intensity | 多情绪及可选强度0—10；迁移不虚构强度 |
| tags | 场景标签，旧数据为空 |
| title / text | 标题与正文 |
| photos | 图片id和应用自有相对路径；拒绝绝对路径和路径穿越 |
| reflection | 场景、事实、需要、下一步，可为空 |
| favorite / legacyId | 收藏状态与原始id |

第一阶段只建立照片/整理结果等字段和序列化校验；照片选择、复制、清理、应对卡编辑界面等在后续步骤实现。旧日期映射到本地当日零点，明确标记day，页面继续使用原date展示。

## 迁移与恢复规则

Preferences 文件名称保持 `zhiyu_journal`：

1. 已有 `record_document_v1` 时，严格校验 `schemaVersion = 1` 和字段，读取后不再迁移旧键。
2. 缺少新版键时，读取 `entries`、`bottles`、`joys`，完整转换后再写入新版文档并flush。
3. id使用类型前缀，避免旧手记和瓶子使用相同时间戳而碰撞。同类型重复id直接阻止迁移，不静默丢弃任何记录。
4. 旧键保留原字节、不再写入，作为升级时原始数据来源。缺少旧键按空列表处理；损坏、null或类型错误不能被当作空列表。
5. 后续写入之前，将当前有效文档存为 `record_document_previous_v1` 并flush。只有新文档flush成功后才更新内存和页面。
6. 写入失败时恢复此前文档；首次迁移失败则移除未完成的新键。恢复也失败时禁用进一步写入，页面提示失败并保留输入。
7. 新版文档损坏或版本过新时阻止写入，不自动回退到旧键，避免恢复已经删除的旧记录。
8. 同时保存时拒绝第二个操作并提示重试，避免两个旧快照互相覆盖；手记另有重复提交保护。

开发恢复：先复制完整Preferences文件留档；检查新版文档与previous文档的有效性和时间，再由开发工具恢复确认过的有效文档。禁止直接删除新键来“修复”已使用的新版，因为那会重新迁移升级时旧数据、丢失升级后的修改。应用内导出/备份恢复界面仍属于第10步。

注意：旧键和previous文档用于迁移/故障恢复，因此当前删除是从有效文档移除，不代表清除所有恢复副本。第10步“删除全部数据”必须覆盖这些键及媒体文件。

源码恢复：在独立目录解压快照进行比较，或从基线提交取回指定文件；不要直接覆盖当前工作区。源码回滚不会自动把新版用户数据转换回旧版本。
